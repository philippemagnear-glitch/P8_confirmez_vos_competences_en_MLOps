# Plan de tests de l’API de scoring crédit

L’API Gradio reçoit une ligne préparée contenant les **310 clés** attendues par le modèle. Un programme tiers utilise `/schema` pour connaître les champs et `/predict` pour obtenir un score. La suite de tests utilise un JSON de référence complet, indépendamment du CSV de démonstration. Pour chaque cas de rejet, on modifie un seul élément de la ligne de départ. Le périmètre couvre `app/main.py` et `app/prediction.py`. Les tests d’intégration utilisent les endpoints Gradio `/predict` et `/schema`.

## Tests à automatiser

| ID | Test et raison de le faire | Cas concret et résultat attendu |
|---|---|---|
| **T01** | **Clé obligatoire absente · Unitaire.** Détecter une donnée perdue lors de la construction de la requête. | Supprimer entièrement `"OWN_CAR_AGE": null`. L’erreur nomme `OWN_CAR_AGE` et le modèle n’est pas appelé. |
| **T02** | **Valeur manquante déclarée et zéro · Unitaire.** Préserver le sens des données préparées. | Avec `"OWN_CAR_AGE": null` et `"CNT_CHILDREN": 0`, la ligne est acceptée. Le tableau transmis au modèle contient `NaN` pour l’âge de la voiture et `0` pour le nombre d’enfants. Un `null` à la place de `false` pour `OWN_CAR_AGE_ANOMALOUS` est refusé. |
| **T03** | **Structure, champs et types incorrects · Unitaire.** Arrêter une requête dont le contenu est incompatible avec le modèle. | Refuser une liste à la place d’un objet, la clé supplémentaire `TARGET`, le texte `"180000.0"` pour le revenu, `1.5` pour le nombre d’enfants, `0` pour `OWN_CAR_AGE_ANOMALOUS`, un nombre non fini et un entier trop grand pour son type. Chaque cas est rejeté avant le calcul. |
| **T04** | **Valeurs hors plage · Unitaire.** Détecter une valeur incohérente même quand son type est correct. | Appliquer les six familles de règles ci-dessous. Pour chaque règle confirmée, vérifier une valeur acceptée et une valeur refusée. Quand une borne est définie, vérifier la borne. Le rejet nomme le champ et explique la règle. |
| **T05** | **Ordre des colonnes · Unitaire.** Deux programmes peuvent envoyer les mêmes clés dans un ordre différent. | Mélanger les clés du JSON. Le modèle reçoit les mêmes valeurs et les colonnes dans le même ordre. La comparaison porte sur le tableau transmis au modèle. |
| **T06** | **Probabilité de défaut et seuil · Unitaire.** Vérifier que l’application sélectionne la probabilité de la classe de défaut et prend la bonne décision au seuil. | Un modèle simulé renvoie des probabilités connues. L’application sélectionne celle de la classe `1` quel que soit son emplacement. Avec un seuil de `0.5`, des scores de `0.49`, `0.50` et `0.51` donnent respectivement les classes `0`, `1` et `1`. |
| **T07** | **Score invalide renvoyé par le modèle · Unitaire.** Éviter de transmettre une probabilité inutilisable. | Simuler des scores de `-0.1`, `1.2`, `NaN` ou l’infini. Le calcul échoue. Les bornes `0` et `1` sont acceptées. |
| **T08** | **Prédiction réelle via `/predict` · Intégration.** Vérifier la chaîne complète, du programme appelant au vrai modèle. | Avec le JSON complet utilisé lors de l’essai Gradio et le même artefact de version `4`, l’API retrouve le score `0.17086662346702958` à une faible tolérance numérique près, la classe `0`, le seuil `0.5`, le nom `credit_scoring_lightgbm` et la version `4`. Toute autre ligne ou version requiert sa propre référence vérifiée. |
| **T09** | **Erreurs reçues par le programme tiers · Intégration.** Permettre à l’appelant de distinguer une donnée à corriger d’une panne du calcul. | Une clé absente déclenche un message qui la nomme. Une panne simulée du modèle sur une requête valide, par exemple une `ValueError` interne, déclenche un message public générique. Les journaux signalent l’échec et préservent les données sensibles de la requête. |
| **T10** | **Schéma fourni par `/schema` · Intégration.** Donner au programme tiers les informations nécessaires pour préparer sa requête. | L’endpoint retourne les 310 champs distincts, tous obligatoires, avec leurs types. Il indique notamment que `OWN_CAR_AGE` accepte `null` et que `OWN_CAR_AGE_ANOMALOUS` attend un booléen et refuse `null`. Ces indications correspondent à T01 et T02. |

## Règles de valeur pour T04

Les règles portent sur les valeurs numériques renseignées. Toutes les clés sont obligatoires. Un `null` numérique explicite reste accepté et le zéro conserve sa valeur. Le tableau fixe les règles à appliquer et précise celles qui dépendent d’une convention de données. Pour ces dernières, utiliser la définition du champ, une règle explicite dans le code de l’API ou un contrat d’entrée disponible. En l’absence de règle établie, conserver le comportement actuel et indiquer la décision en attente. Les valeurs observées dans une seule ligne constituent des exemples.

| Famille retenue | Règle à appliquer | Exemples |
|---|---|---|
| **Âge de la voiture** | `OWN_CAR_AGE ≥ 0` quand l’âge est renseigné. | Accepter `0`. Rejeter `-1`. |
| **Âge du demandeur en jours relatifs** | `DAYS_BIRTH < 0` selon le codage relatif présent dans les données préparées. La naissance précède la demande de crédit. | Accepter `-12994`. Rejeter `0` et `+12994`. |
| **Heure de la demande** | Appliquer la plage `0–23` à `HOUR_APPR_PROCESS_START`, l’heure de la journée de la demande. | Accepter `0` et `23`. Rejeter `-1` et `24`. |
| **Comptages et jours de retard** | Exiger une valeur supérieure ou égale à zéro pour les champs qui comptent des éléments ou mesurent une durée de retard, par exemple `CNT_CHILDREN`, `BUREAU_CREDIT_COUNT` et `BUREAU_MAX_DAYS_OVERDUE`. Identifier les champs concernés à partir de leur définition. Respecter leur type actuel. | Accepter `0` pour le nombre d’enfants et `7.0` pour le nombre de crédits encodé en décimal. Rejeter `-1` pour un compteur ou une durée de retard. |
| **Autres dates en jours relatifs** | Appliquer une borne supérieure de `0` quand le champ désigne exclusivement un événement passé ou survenu le jour de la demande. Vérifier le codage de chaque champ et le traitement des valeurs spéciales, notamment pour `DAYS_EMPLOYED`. | `DAYS_EMPLOYED = -2055.0` est cohérent. Le traitement d’une valeur positive dépend de sa signification dans les données préparées. |
| **Montants, soldes, moyennes et autres rapports** | Retenir une borne seulement lorsqu’elle découle de la définition du champ ou de sa formule. Vérifier notamment le traitement d’un revenu nul et la convention de signe des soldes. | Le rapport `PREV_APPROVED_CREDIT_TO_APPLICATION_RATIO_MEAN = 1.0594774772` de la ligne de référence doit passer. Le rejet de `AMT_INCOME_TOTAL = 0` exige une règle établie pour le champ préparé. |

## Exécution automatique et couverture

- Créer le workflow GitHub Actions `.github/workflows/tests-api.yml`. Sur les `push` et `pull_request`, un job installe les dépendances selon les fichiers du dépôt, lance les tests avec `pytest` et affiche la couverture des lignes et des branches. Un test en échec fait échouer le job.
- Mesurer les lignes et les branches couvertes dans `app/prediction.py` et le code API de `app/main.py`. Donner les résultats par fichier et relever les chemins critiques non exercés. Le taux de couverture complète les assertions du tableau.
- Faire tourner les tests unitaires et les appels d’intégration avec un modèle simulé dans la CI. Exécuter aussi T08 lorsque l’artefact version 4 et le JSON de référence exact sont accessibles au job. Si l’un manque, afficher le motif de l’omission dans le rapport. Indiquer la commande locale qui reproduit la suite.
- Utiliser `pytest-cov` pour le rapport de couverture et respecter la gestion de dépendances du dépôt. Si le projet utilise `uv` et possède un `uv.lock`, installer les dépendances à partir de ce verrou.
